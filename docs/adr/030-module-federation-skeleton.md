# ADR 030: Module Federation skeleton, and what was checked (Phase 2)

Status: accepted

The three builds (`shell`, `people`, `delivery`) run standalone and hosted from one build each, with placeholder screens only. This ADR records which plan assumptions held on the pinned versions, the workarounds, and the choices made where the plan left room. Versions: Rsbuild 2.2.11, `@rsbuild/plugin-react` 2.1.1, `@rsbuild/plugin-typed-css-modules` 1.2.4, `@module-federation/rsbuild-plugin` and `@module-federation/enhanced` 2.9.2, React 18.3.1, React Router 7, Rstest 0.12.3.

## Decisions

1. **One `components-<app>` Rstest project per app**, not one shared `components` project. A project extends one Rsbuild config, and each app has its own CSS Modules prefix. Each project is jsdom, includes `apps/<app>/src/**/*.test.{ts,tsx}` (except `src/data/`, which runs in the Node `domain` project), and loads a per-app `test-setup.ts` that registers the `jest-dom` matchers and cleans up after each test. ADR 014's matcher typing workaround is a `jest-dom.d.ts` in each app.
2. **Only `react` and `react-dom` are shared** (`singleton: true`, `requiredVersion: ^<installed version>`, so it follows the catalog). `react/jsx-runtime` and `react-dom/client` are not listed: they are thin wrappers that call the shared `react` and `react-dom`. The singleton readout therefore compares `useState` (from `react`) and `flushSync` (from `react-dom`), not `createRoot`, whose wrapper differs per app.
3. **Singleton proof (T2.7)** has three parts. Each remote's `./App` module records its `react` and `react-dom` in `window.__BASELINE_REACT__`; the shell's `ReactReadout` shows the versions and whether each is the shell's own instance ("One React across all loaded apps."); and the placeholders use `useState` from the remote's own import, so a second React would fail with an invalid hook call. Tests for `mount().update()` show state surviving a context update.
4. **The remote's router is created in an effect and disposed on unmount** (`useBrowserRouter`), because `createBrowserRouter` adds a `popstate` listener when it is created. Creating it during render would leak a listener per StrictMode double render. The shell's own router is created once at module level.
5. **Design tokens are read through an override hook.** `tokens.css` declares `--bl-color-primary: var(--bl-theme-color-primary, #2456d6)` on `[data-baseline-root]`. A hosted remote's root sits inside the shell's panel container and declares the token itself, so a value set on the container as `--bl-color-primary` would be shadowed. The shell sets `--bl-theme-color-primary` instead, which inherits down and is read at the remote's root. Checked with `?theme=contrast` on the shell: the primary button went from `rgb(36, 86, 214)` to `rgb(122, 31, 162)`. The remote keeps its own defaults, so it needs nothing from the shell's `ui` version. `tokens.css` is imported by each app's `App.tsx` (`@baseline/ui/tokens.css`), so it travels with the exposed module.
6. **`?break=people` (T2.6)** swaps that remote's URL for `/__broken__/people/remoteEntry.js` after the config is loaded and resolved (`applyBreak`, pure and unit-tested). It accepts a comma list. The shell boot, the panel and the retry are unchanged by it. `?theme=contrast` is the matching debug switch for tokens.
7. **Panel host (T2.5).** `RemotePanel` wraps the lazy remote in `Suspense` and the `ui` `ErrorBoundary`. The loader (`remoteLoader.ts`) caches one promise per remote, forgets a failure, has a 10 s load timeout (`RemoteLoadTimeoutError`) and re-registers the remote with `force: true` before retrying. A lazy component keeps its first result forever, so Retry builds a new one. Both remotes are loaded at boot, so the readout does not wait for a visit, and each panel reuses that load.
8. **The standalone host context** is built in the remote (`standalone.ts`): EUR, the stub user `user-1`, `basePath` from `document.baseURI`, and `navigate` opening `/remotes/<other>/…` on the same origin. In dev that URL does not exist (the remotes run on separate ports), which is fine while the skeleton has no cross-app links. Phase 5 and 6 decide whether to hide those links.
9. **`<base href>`** is added through `html.tags` in each remote's Rsbuild config: `/` for `dev`, `/remotes/<name>/` for `build`. The container entrypoint rewrites the built value. The shell has no `<base>`; its asset URLs are absolute (`output.assetPrefix: '/'`), and its deep links reload correctly.

## Checked in a browser (playwright-cli)

With the three dev servers on 3000, 3010 and 3020, and with the three builds served by a scratch static server (no Docker) on port 4100 with the SPA fallback described in ADR 029:

- Hosted: `/` redirects to `/people`; both remotes render; the counter in each placeholder keeps its state (hooks work across the boundary); Delivery deep link, invalid id ("Not found. That is not a valid project id.") and back button all work; `aria-current` follows the first path segment.
- Standalone: `:3010` and `:3020` render; a deep-link reload (`/emp-003`, `/prj-1`) works; an invalid id gives the inline "not found".
- `?break=people`: the People panel shows "People could not be shown." with Retry; the nav and Delivery keep working; `?break=delivery` leaves People working. A 404 on `remoteEntry.js` and a never-answering `remoteEntry.js` (error after 10.4 s, "did not load within 10 s") give the same in-place error; Retry recovers once the remote is reachable.
- One React: `shell`, `people` and `delivery` all report React 18.3.1 and "same instance as shell", in dev and in the production builds.
- Path independence: the People build (made for `/remotes/people/`) served from `/elsewhere/people/` loaded standalone (with a deep-link reload) and hosted, with no non-200 request and the CSS applied.
- CSS: the production builds extract CSS to files; class names carry the app prefix for `ui` too (`bl-people-button-…`, `bl-delivery-button-…`); the built CSS contains only `.bl-<app>-…` selectors, `[data-baseline-root]` and prefixed keyframes, so nothing leaks.

Not verified in a browser: the Docker and nginx paths (the Docker setup, T2.9, wires `BASE_PATH`, `config.json` and the gateway), and `docker compose stop people`.

## Consequences

- Adding a remote means a route, a `RemoteRoute` and an entry in `REMOTE_NAMES` and the config schema.
- Node 22 ran everything here although `.nvmrc` says 24; nothing in the frontend depends on the difference.
- Each app lists its own test libraries as devDependencies. The root has them too, but the root copies resolve React 19 and are not used by these tests.
